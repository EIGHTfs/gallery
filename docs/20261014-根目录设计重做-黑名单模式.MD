# 根目录设计重做：白名单「根」→ 自由浏览 + 黑名单排除（2026-10-14）

## 一、为什么要重做（现状问题）

现行设计是「根白名单」：`GALLERY_FS_ROOT` / `config.fsRoot` 指定**一个**浏览根，或由 `config.directories`
的公共前缀推导出一个根；所有请求都要「落在该根之内」（`browseRoot` / `resolveBrowseLimit`）。

实测出来的三个毛病：

1. **跨卷就退化成 `/`**：目录分布在 `/volume6` 与 `/volume10` 时，公共前缀算到 `/` —— 既没表达出「只允许这两棵树」，
   又等于放开全盘浏览（想拦的没拦住，想放的说不清）。
2. **加一个盘就得改模型**：本次要加 `/volume10/Resource/(Pawchive)/Pawchive`，发现它是「另一个根」——
   白名单模型下只能再去扩 `fsRoots`（多根），而多根还要同步改浏览校验与全量扫描，成本被模型放大。
3. **语义不对**：用户真正想表达的是「除了系统关键目录，别的随便看」，而不是「只看我列的几棵子树」。

## 二、新设计：自由浏览 + 黑名单排除

**允许**：任意绝对路径（目录树可任意下钻、面包屑可上溯）。
**拒绝**：`realpath` 解析后落在**黑名单**内的路径及其子路径 ⇒ 返回 403。

要点：

1. **黑名单 = 系统关键目录数组**，可配置：
   - `.env`：`GALLERY_BLACKLIST_DIRS=/etc:/proc:/sys:…`（分隔符 `:` 或 `,`，与 `GALLERY_FS_ROOTS` 一致）
   - `config.json`：`blacklistDirs: ["/etc", …]`（`.env` 覆盖 config）
   - 未配置时用内置默认（见下），但**内置默认只是兜底**，部署方应显式声明自己机器的关键目录。
2. **匹配规则**：先把请求路径与黑名单项都做 `fs.realpathSync`（不存在则退回 `path.resolve`），
   再按「等于 或 以 `项 + sep` 开头」判定 ⇒ **防符号链接绕过**（软链指到 `/etc` 也拦）。
3. **默认黑名单（Linux / 群晖 NAS 兜底集）**：
   `/proc` `/sys` `/dev` `/run` `/boot` `/etc` `/bin` `/sbin` `/lib` `/lib64` `/usr` `/var` `/tmp`
   `/volume1/@appstore` `/volume1/@appdata` `/volume1/@database` `/volume1/@tmp` `/volume1/docker`
   `/volume2`…`/volumeN` 下的 `@*` 元数据目录（按 realpath 前缀匹配，不做通配扩展，避免误伤用户数据）
4. **`config.directories` 语义变更**：从「权限边界」降为「**快捷入口 + 分类标签**」——
   前端目录树/分类仍按它展示；但浏览**不再**受它限制。
5. **扫描范围**：全量索引仍只扫「已配置目录」（避免全盘扫描拖垮 NAS，低负载纪律）；
   浏览到未索引的目录时按需扫描该目录（现有按需行为不变）。
6. **兼容**：`fsRoot` / `fsRoots` / `GALLERY_FS_ROOT` / `GALLERY_FS_ROOTS` 保留为「**若显式配置则退回白名单模式**」
   （老部署行为不变）；**都不配置时默认黑名单模式**。这样不用强制迁移，也能让新部署用上新语义。

## 四、验收标准（全部要实测）

1. `/volume10/Resource/(Pawchive)/Pawchive` 能在前端浏览（分类 `pawchive-pw` 下出现、目录可展开、图片可看）。
2. `/etc`、`/proc`、`/volume1/@appdata` 等请求被拒（403），且**软链指向黑名单**同样被拒。
3. 前端目录树/面包屑在「非配置目录」里也能正常工作（不再被 clamp 回公共前缀）。
4. 全量测试通过（含新增黑名单用例）；渲染点基线若新增渲染点则显式更新。
5. 部署端实测：加目录 → 前端可见可浏览；黑名单项被拒。

## 七、已确认决策与实测数据（2026-10-14）

**已确认**：

1. **默认黑名单 = 兜底集（A 档）**：`/proc /sys /dev /run /boot /etc /bin /sbin /lib /lib64 /usr /var /tmp` +
   群晖元数据 `/volume1/@appstore /volume1/@appdata /volume1/@database /volume1/@tmp /volume1/docker`。
   部署方可用 `.env` 的 `GALLERY_BLACKLIST_DIRS`（全量替换）或 `config.blacklistDirs` 覆盖/收窄。
2. **扫描范围 = 分层索引，但默认「不限制」**（2026-10-14 当日修订）：全量索引默认索引**所有层级**
   （保持既有行为）；需要给超大根限深时，用 `.env` 的 `GALLERY_SCAN_MAX_DEPTH` 显式设置
   （例：`=2` 只扫配置根往下 2 层，更深层进入该子目录时按需扫描）。
   **修订原因（回归）**：最初把默认值定为 2，导致配置根下**超过 2 层**的文件夹（如「角色」目录）
   不再进索引、前端不显示 —— 深度限制不能当默认，只能作为超大根的显式手段。

**实测规模（这就是为什么必须分层索引）**：

| 路径 | 顶层子目录 | 全树图片 | 全树压缩包 |
|---|---|---|---|
| `/volume10/Resource/(Pawchive)/Pawchive` | 461 | **341,523** | 21,383 |

**事故记录（务必遵守低负载纪律）**：一次带 `noCache=true` 的请求触发该根的全量扫描，日志出现
`scan:stat 160 GB ×159,220` 且持续上涨、读 6.3 MB/s，明显拖慢 NAS；已用项目自带 `./start.sh restart`
中止（重启即终止旧进程内的扫描）。**结论：任何验证都不要对该量级的根使用强制重扫。**

> 补充（2026-10-14 晚）：曾按「默认 2 层」实现的分层索引已**取消**（默认改为不限制），
> 因为它导致配置根下超过 2 层的文件夹（如「角色」目录）不再进索引、前端不显示（回归）。

## 八、待实现：「访问时按需索引」（用户确定的策略，尚未实现）

**现状**：`apiImages` 的 `recursive=true` 分支会对被请求目录做**整棵子树**扫描 ——
配置根是 34 万张图的那种量级时不可行，也正是「进入该根前端显示 0 张」的原因（索引建不出来）。

**目标**：索引只在该目录**被访问时**顺便建 —— 请求哪个目录就只索引那个目录，永不整树扫描。

**落地点（已定位，照此改即可）**：

1. `server/routes/browse.js` `apiImages`：
   - `recursive=true` 分支：把 `recursiveScanAll(searchPath)`（整树）换成「只列 `searchPath` 自身文件」的单层扫描 + 按目录缓存；
   - 直接子目录名交给**已存在**的 `/api/directories`（纯 readdir、零扫描），供前端渲染「可进入的目录项」；
   - 缓存键仍用 `searchPath`（现在是单层结果），并在响应里带上 `dirs`（或让前端另调 `/api/directories`）。
2. 前端 `js/browse/render.js`：
   - 当前目录**没有直图**时，仍渲染「子目录项」（数据来自 `/api/directories`），点击即 `currentPath` 下钻；
   - 这样 `/volume10/Resource/(Pawchive)/Pawchive` 顶层 461 个目录立刻可见、可逐层进入，且**永不触发整树扫描**。
3. **验收（必须真渲染，且不许只看接口）**：
   - 进入该根 → 看到目录项（不是「0 张」）；进入任意子目录 → 只扫该子目录（看耗时与日志，不出现整树 scan）；
   - 既有文件夹（如各游戏的「角色」深层目录）显示**不回归**。
4. **风险提示**：上次「深层文件夹不显示」的回归正是动扫描范围引起的 ⇒ 本项**必须真渲染验证通过后**才提交、才上线。

## 九、按需索引（用户方案，取代「深度」思路）—— 设计契约

**用户方案原话要点**：索引文件分成多个，按分类再按目录；9 个大分类就是 9 个索引大文件夹；
**粒度 = 每个目录一个索引**；实际访问哪个页面之前，只读那个页面的索引。

### 9.1 索引存储布局

```
<索引根>/<分类名>/<目录路径 slug>/index.json      ← 每个目录一个文件，只描述该目录自身的直接图片
```

- 文件内容（示意）：`{ dir, category, ts, dirMtime, images: [{name, path, url, size, mtime}] }`
- `slug`：目录相对路径 → 可读化（`/` 与不安全字符替换为 `__`）；保留可读性便于人工排查与备份
- 分类维度来自 `config.categories`；`config.directories` 提供「分类 → 根目录」的入口映射

### 9.2 生成与读取时机（这就是「按需」）

1. **读取**：进入某页面（= 某目录）时，**只读该目录的索引文件**；没有整树扫描。
2. **生成**：该目录索引不存在、或目录 `mtime` 比索引记录更新 ⇒ **只扫该目录本身**（单层 readdir + stat + 图片过滤），写回索引。
3. **子目录**：不预扫；子目录名由 `/api/directories`（纯 readdir）提供，供前端渲染「可进入的目录项」。
4. **重建入口**：支持按目录 / 按分类 / 全量重建（脚本或 API），用于批量导入后一次性补齐。

### 9.3 接口与前端

- `/api/images?root=&path=`：命中目录索引则读索引；否则单层建索引后返回；响应可带 `dirs`（子目录列表）或前端另调 `/api/directories`。
- 前端 `browse/render.js`：进入目录才取数；**无直图时也渲染子目录项**（可点击 `currentPath` 下钻）。

### 9.4 验收口径（必须真渲染）

1. 进入 `/volume10/Resource/(Pawchive)/Pawchive` 顶层 → 立刻看到 461 个可进入的目录项（不是「0 张」）。
2. 进入任意子目录 → 只扫那个子目录（日志与耗时可见，**不出现整树 scan**，不出现 `scan:stat` 数十 GB）。
3. 既有深层文件夹（各游戏「角色」目录）显示**不回归**。
4. 索引文件按分类-目录生成，可单独删除/重建而不影响其它分类。
