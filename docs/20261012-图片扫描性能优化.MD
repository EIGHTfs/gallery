# 拾光集（gallery）图片扫描性能优化方案

> 本方案仅为设计草案，**未实际修改任何代码**。请审核确认后再执行。
> 看板模式：确认后逐项执行并标记完成。执行纪律：先学后做、从简到难、每步小提交、最后整理。
> 中断管理：执行中插入新需求默认不执行，记录后继续原任务。

---

## 一、修改目标

- **问题描述**：读取 mod 目录图片的**全树扫描是纯同步递归**（`server/lib/scan.js` 的 `recursiveScanAll`：
  `readdirSync` 递归 + **每个图片文件一次 `statSync`** + 每个目录一次 `statMtime`），冷扫描期间
  **占满事件循环**，服务在扫描结束前无法响应其它请求。gallery 已实际部署且带自动更新，卡顿会直接影响使用。
- **期望效果**：
  1. 冷扫描（缓存失效后的首次扫描）期间，`/api/status`、`/api/io` 等接口**仍能正常响应**（不再整段堵死）；
  2. 扫描本身的墙钟耗时不劣化（允许略增，换取可响应性）；
  3. 扫描成本可归因——能回答「哪一行、哪个目录在吃 IO」。
- **成功标准（webapi 实测，可复现）**：
  - 触发一次冷扫描（`noCache=true`），扫描期间每 2 秒请求 `/api/status`，**超时次数 = 0、最大延迟 < 1s**
    （对照：优化前应能观察到秒级~十秒级无响应）；
  - `GET /api/io` 返回 `bySite`，且能列出扫描相关的调用点与字节/次数；
  - 冷扫描总耗时与优化前同一量级（回归不允许超过 +50%）。

## 二、潜在问题分析（AI 必补）

| 风险类型 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| 性能退化 | 中 | 异步化 + 并发 stat 可能因并发过高反而变慢 | 并发上限（如 8–16）+ 实测对比；**先量后改**（perf-profile-first） |
| 兼容性破坏 | 低 | `/images` 响应结构若变动会破坏前端 | **不改响应结构**；只改内部扫描实现，前端消费字段保持不变 |
| 安全漏洞 | 低 | 扫描路径来自 `root` 参数 | 保持现有路径校验逻辑不动；不新增对外输入面 |
| 依赖冲突 | 低 | 若引入第三方并发库会破坏零依赖 | **零依赖**：只用 `fs.promises` + 手写并发池 |
| 数据丢失 | 低 | 扫描只读，不写用户数据 | 全程只读；不做删除/移动 |
| 自动更新回滚 | 中 | gallery 带 auto-update，改动随更新下发到部署端 | 改动走 git 提交 → 自动更新拉取；出问题可回退到上一 commit（部署端 start.sh 可重启） |
| 模板回流遗漏 | 中 | gallery 由 `assemble.json` 组装，若改到下发件而没回流模板，下次组装会被覆盖 | 先查 `assemble.json` 映射；下发件一律**改模板再组装**（模板一致性门禁会拦） |

**额外边界条件检查**：

1. 目录为空 / 只有排除目录（`@eaDir`）/ 根目录不存在 → 扫描应返回空列表且不抛错（现状已 try/catch 吞掉，需保持）。
2. 扫描过程中文件被删除/无权限 → 跳过该文件，不中断整轮扫描（现状已处理，异步化后需保持同等容错）。
3. 多个请求**并发触发**同一根的冷扫描 → 现状会各自扫一遍（重复劳动）；需加**单飞（in-flight 复用）**，
   否则并发越高扫描越多次（本次一并处理）。
4. 符号链接 / 环形目录 → 现状未处理；异步化后需保持同样行为（**不新增**跟链行为，避免无限递归）。
5. 超大树（十万级文件）→ 内存中一次性收集 images 数组，需确认可接受；本次不引入流式返回（留后续清单）。

| 是否有社区最佳实践？ | 有 | 大目录遍历用「有界并发 + 分批让出」；缓存用 mtime 探针（本项目已实现） |
| 是否有现成的库/工具可用？ | **有（但不用）** | `fast-glob`/`globby` 等；本项目零依赖，手写即可，避免引依赖 |

### 3.2 学习结论

- **学到的关键点**：
  1. **先读代码再断言**：本次口头初判「每次请求都 stat 全部目录」是**错的**——`scan.js:19` 已有
     `IMAGE_PROBE_INTERVAL = 30s` 探针节流。真正的问题只有「同步扫描阻塞事件循环」这一类。
  2. 同类问题在 gbmd 已有成熟解法：**长同步循环每 N 次让出事件循环**（总耗时不变、服务保持可响应）。
  3. 「结果对、代价错」的缺陷常规断言测不到，必须靠**探针/计数**（`perf-profile-first`）。
- **决定复用的方案**：
  - 事件循环让出点（gbmd `finalizeHtmls` 已验证：74 秒堵死 → 0 次超时）；
  - **直接移植 gbmd 的 `io-monitor`（含 `bySite` 按调用点归因）** 作为本次的测量工具（gallery 目前**无任何 IO 探针**）；
  - 扫描缓存 + mtime 探针**保留不动**（设计正确，不动它）。
- **决定不用的方案及原因**：
  - 引入 `fast-glob` 等依赖 → 破坏零依赖约定；
  - 把扫描搬到 worker_threads → 改动面过大、收益不确定，留后续清单；
  - 缩短/取消 30s 探针节流 → 会加剧请求路径开销，方向相反。

## 五、逐文件改动详情

### 5.1 `server/lib/scan.js`（核心）

- **当前位置**：`recursiveScanAll`（第 30–65 行）、`scanCacheStillValid`（第 68–74 行）。
- **当前逻辑**：同步递归 `readdirSync` → 每个图片 `statSync`（取 size/mtime）→ 每个目录 `statMtime` 记录探针。
- **改动内容**：
  1. `recursiveScanAll` 改为 `async`，内部用 `fs.promises.readdir` 逐目录展开（**BFS 队列**，非递归），
     每处理 N 个目录 `await new Promise(r => setImmediate(r))` 让出事件循环（N 取 20–50，实测后定）；
  2. 图片 `stat` 用**有界并发池**（上限 8–16）异步执行，避免「串行等 stat」拖长墙钟，也避免并发过高打爆 IO；
  3. 新增**单飞复用**：同一 `searchPath` 的并发冷扫描共享同一个 Promise（避免并发请求各扫一遍）；
  4. `scanCacheStillValid` 的探针 stat 也改为异步（批量 `fs.promises.stat`，同样有界并发）；
  5. **保持导出面不变**（`IMG_EXT_RE`/`ZIP_EXT_RE`/`IMAGE_SCAN_CACHE`/`IMAGE_PROBE_INTERVAL`/`statMtime`/
     `recursiveScanAll`/`scanCacheStillValid`），只把 `recursiveScanAll`/`scanCacheStillValid` 变成 async。
- **改动原因**：同步全树扫描会占满事件循环（与 gbmd 实测的 74 秒堵死同类）。
- **潜在影响**：所有 `require("./scan")` 的调用方必须 `await`（`routes/gallery.js` 等，见 5.2）。

### 5.2 `server/routes/browse.js`（`/api/images` 实际所在处；**已核实，不是 routes/gallery.js**）

- **当前位置**：第 76–77 行（缓存失效 → `recursiveScanAll(searchPath)`）、第 242 行（另一处 `scanCacheStillValid`）。
- **改动内容**：两处调用改 `await`（`await scanCacheStillValid(cached)` / `await recursiveScanAll(searchPath)`）；
  路由处理器本身已是 async（沿用既有写法）；**响应 JSON 结构完全不变**（`{ images: [...], ... }`），前端零改动。
- **潜在影响**：`scan.js` 另有两个**非扫描**使用方只取常量——`lib/gif.js:14`、`lib/archive.js:12`
  都只 `require("./scan")` 拿 `IMG_EXT_RE` ⇒ 不受 async 化影响（但**导出面必须保持**，已在 5.1 约定）。

### 5.3 `server/lib/io-monitor.js`（新增，从 gbmd 移植）

- **内容**：与 gbmd 同实现：`meter(label, site?)`（站点**创建时**固定，零 per-call 开销）、
  `count(label, bytes, site?)` 兼容、`snapshot()` 返回 `byLabel` + **`bySite`**、`[io]` 日志带最热调用点。
- **移植后在扫描路径埋点**：`scan:readdir`（目录数）、`scan:stat`（图片 stat 次数/字节）、`probe:stat`（探针）。
- **原因**：gallery 目前**无任何 IO/性能探针**，扫描慢时无法归因（本次要先能看见，再谈优化）。

### 5.4 `server/routes/settings.js` / `server/app.js`

- 新增鉴权路由 `GET /api/io` → `ioMonitor.snapshot()`；启动时 `ioMonitor.start({ intervalMs: 10000, logThresholdMBps: 2 })`。

### 5.5 `test/*.cjs`（新增，脚本一律放 `test/`）

- `io-monitor.test.cjs`：直接沿用 gbmd 版本（5 条，含 10 万次调用 < 400ms 的性能护栏）。
- `scan-async.test.cjs`：**等价性**（同一临时目录树，异步扫描结果与同步实现逐字段一致）、
  空目录/不存在根/无权限文件不抛错、**并发单飞**（同时发起 3 次冷扫描，实际只扫 1 次）。

> 每解决一个问题（bug/踩坑/性能/平台/流程）**当场**固化，不等收尾。结构四要素：现象 / 根因 / 解决 / 防再犯。

### 12.1 本次**已可固化**的两条（读代码阶段就产生了）

**① 「先读代码再断言」——口头判断被源码纠正**

```
现象：初判「/images 每次请求都 statSync 全部已知目录，上万目录即上万次同步 stat」，
      据此排出了优化点 2；实际读 server/lib/scan.js 发现第 19 行已有 IMAGE_PROBE_INTERVAL = 30s 节流，
      探针在 30 秒内不重复执行 ⇒ 该判断错误。
根因：拿「缓存/节流通常没做」的常见印象替代了读码；而本项目 scan.js 头部注释就写着「探针」策略。
解决：改为先通读 scan.js（84 行）+ routes/gallery.js 全文，再下结论；修正后的真问题只剩
      「全树扫描纯同步、无让出点」这一类。
防再犯：① 断言任何「每次请求都做 X」之前，必须先 grep 到该 X 的调用点并读上下文；
        ② 项目里已有「缓存/探针/节流」类注释时，优先验证它是否生效，而不是假设没做。
落点：ai-work-archive/skills/（通用方法论，追加进 verify-before-diagnose 或 debug-fix-mistakes）
```

**② 「同步全树扫描必须留让出点」——同项目已复现两次**

```
现象：gbmd 的 finalizeHtmls 纯同步逐目录处理，把 /api/* 连续堵死 74 秒（实测：8 秒超时连续 9 次）；
      gallery 的 recursiveScanAll 是同一形态（readdirSync 递归 + 每图 statSync），冷扫描同样会堵死服务。
根因：Node 单线程——长同步循环期间事件循环无法处理任何请求；总耗时看着不长（秒级），
      但期间服务等于不可用，用户侧表现为「点一下就卡住」。
解决：长循环每 N 次迭代 `await new Promise(r => setImmediate(r))` 让出（gbmd 实测：收尾期间
      接口超时 0 次、最大延迟 0.606s，总耗时不变）；配合有界并发处理 per-file I/O。
防再犯：① 任何「遍历整棵树/整张大表」的同步循环，落地前先问「这期间服务还能响应吗」；
        ② 配套写一条性能护栏测试或 webapi 验收项（扫描期间接口延迟 < 1s）。
落点：ai-work-archive/skills/（追加进 perf-profile-first 的「防再犯判据」一节）
```
