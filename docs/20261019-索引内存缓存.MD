# 索引内存缓存：gallery 读路径性能优化（设计方案）

> 状态：**待确认**（未改动任何代码）
> 基准点：`perf-baseline-20261019`（gallery `4226302` / bench-template `19eb167`，工作区干净）
> 说明：本方案按「设计角度」撰写；全部落地并验证后，按使用角度重写为功能介绍。

---

## 一、修改目标

- **问题描述**：`/api/images` 每次请求都从磁盘重读整份分类索引（无内存缓存），大分类索引达 94MB / 21237 行。
- **期望效果**：同一分类的重复请求不再扫盘，热路径耗时显著下降；首次冷读后即进入内存。
- **成功标准（端到端，冷热分开记）**：
  - 热态（缓存已命中）：原神 `/api/images?recursive=true` 从 **1.5–1.65s** 降到 **≤ 0.5s**
  - 冷态（首次）：不劣化（允许与现状持平或略高，因要多做一次缓存登记）
  - 结果**逐字节等价**：同一请求在改前/改后返回的 `{count, images[].path}` 集合完全一致

## 二、潜在问题分析

| 风险类型 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| 性能退化（内存压力） | 中 | 205MB 索引若全部驻留，Node 堆吃紧 | 缓存**按字节上限**（可配，默认 128MB）+ LRU 淘汰；超限只缓存最近用到的分类 |
| 数据不一致（缓存陈旧） | 中 | 目录变动后仍读旧缓存 ⇒ 列表不更新 | 失效键 = **文件 mtime + size**；且所有写路径（`upsertDirEntryJsonl` / `writeAllJsonl` / `rebuild`）**主动失效**该分类 |
| 兼容性破坏 | 低 | 调用方拿到的对象结构变化 | 缓存只包在 `readDirEntryJsonl` / `loadAllJsonl` 内部，**对外签名与返回结构不变** |
| 并发写读竞争 | 低 | 写盘瞬间被读到半份 | 现有 `upsertDirEntryJsonl` 已是 `tmp + renameSync` 原子替换；缓存失效发生在 rename **之后** |
| 回退困难 | 低 | 出问题难恢复 | ①`GALLERY_INDEX_CACHE=0` 一键关闭缓存 ②基准 tag 可整体回退 |

**边界条件检查**：

1. 索引文件不存在（新分类首次访问）⇒ 缓存层返回空 Map/`null`，**不抛错**，行为同现状。
2. 索引文件被外部清空（`rm -rf cache-index`）⇒ mtime/size 变化 ⇒ 自动失效重读，**不会永久读到空**。
3. 同一分类并发请求 ⇒ 缓存是同步读入 + 同步赋值，无 await 间隙，**不会重复回源**（Node 单线程）。
4. 缓存上限为 0 / 非法值 ⇒ 视为关闭缓存（走原路径），不影响正确性。

## 三、Skill 学习检查

| 检查项 | 结果 | 说明 |
|---|---|---|
| 是否已有类似功能的 skill？ | 有 | `perf-profile-first`（先测量再改、等价性纪律）、`perf-diagnosis-method`（分阶段计时、单假设复测） |
| 是否已有同类问题的解决方案？ | 有 | 同 skill 第六节案例：gbmd「高频全量重写状态文件」——同属「每次调用都全量处理」类别；以及 10-18 索引 SQLite 实验结论（**JSONL 优先**，SQLite 是退化） |
| 是否有官方推荐做法？ | 有 | Node 单线程同步 I/O 下，最直接的做法就是「进程内缓存 + 指纹失效」，不引入依赖 |
| 是否有社区最佳实践？ | 有 | mtime+size 作为轻量指纹（等价 `etag`），比每次 stat 内容便宜得多 |
| 是否有现成的库/工具可用？ | 无（项目零依赖） | 用内置 Map + 手写 LRU，不引第三方 |

**学到的关键点**：

1. `perf-profile-first` 铁律：**先 profile 再改**；本次已用「审计性能检测 + 代码定位 + 端到端实测」三方交叉，热点是**无缓存的重复扫盘/解析**，不是 CPU 计算。
2. 10-18 的实测结论：**索引换 SQLite 是退化**（启动 673ms→1.09s、体积 48.5→56.5MB+WAL）⇒ **不要动存储格式**，只在读路径加缓存。
3. 同 skill 第八节教训：**不要跨项目套结论**；本次基线全部取自 gallery 部署端自身。

**决定复用的方案**：进程内 LRU 缓存 + `mtime+size` 指纹失效 + 写后主动失效（最小改动、可一键关闭）。

**决定不用的方案及原因**：
- ❌ 换 SQLite：10-18 已实测退化。
- ❌ 引入 mmap / 第三方库：项目零依赖，且收益不确定。
- ❌ 把索引拆成更多小文件：与既定设计「一个分类一个索引」冲突。

## 五、逐文件改动详情

### 5.1 新增 `server/lib/index-cache.js`

- **当前逻辑**：无（新文件）
- **改动内容**：导出一组纯函数：

```js
// 按「文件 mtime + size」判断缓存是否仍然有效；上限按字节算，超限按最近最少用淘汰。
// 缓存只在同一进程内有效：进程重启后首次访问仍会读盘（这是预期行为，不落盘）。
function fingerprints(file)            // → { mtime, size } 或 null
function getMap(file, loader)          // 命中 → Map；未命中 → loader() 后登记（超限淘汰）
function invalidate(file)              // 写后失效（按文件路径）
function stats()                       // 命中/未命中/淘汰计数，供观测
function setLimitBytes(n) / getLimitBytes()
```

- **改动原因**：把「缓存策略」与「索引格式/业务」解耦，便于单测，也避免 `index-store.js` 继续变长。
- **潜在影响**：仅被 `index-store.js` 引用。

### 5.2 修改 `server/lib/index-store.js`

- **当前实现**：`readDirEntryJsonl()`（约 110–153 行，每次 open + 逐行扫直到命中）、`loadAllJsonl()`（约 214–248 行，每次全量解析）——**两者都没有内存缓存**。
- **改动内容**：
  1. `loadAllJsonl(category)` → 改为 `cache.getMap(jsonlPathFor(category), () => 原实现)`，**原读盘逻辑整体保留**作为 loader。
  2. `readDirEntryJsonl(category, key)` → 优先从同一份 Map 取 `map.get(key)`；未命中再回退原流式扫盘实现（保持「找不到返回 null」语义）。
  3. 三处写路径后各加一次 `cache.invalidate(file)`：`upsertDirEntryJsonl`、`writeAllJsonl`、`rebuild`。
  4. 顶部读取开关：`GALLERY_INDEX_CACHE=0` ⇒ 全部走原路径（不注册缓存）。
  5. 缓存上限：`GALLERY_INDEX_CACHE_MB`（默认 128），**不写死在使用处**。
- **改动原因**：消除「每次请求重扫 94MB / 重解析 21237 行」的重复工作。
- **潜在影响**：`walkWithIndex`（递归遍历）、`getDirEntry`、`entryOf` 三个调用方全部受益，签名不变。

### 5.3 新增 `test/index-cache.test.cjs`

- 覆盖：命中、指纹变化后失效、写后失效、超上限淘汰、`GALLERY_INDEX_CACHE=0` 关闭、文件不存在返回空。
- 用临时目录 + 合成索引（不依赖真实数据 ✓ 符合 `test-design-norms` 的「相对路径/参数派生」）。

## 六、影响分析

| 维度 | 影响程度 | 说明 |
|---|---|---|
| 现有功能 | 低 | 接口签名与返回结构不变；未命中时行为与原实现一致 |

| 可维护性 | 中（正向） | 缓存策略独立成文件、可单测；`index-store.js` 只多几行调用 |

## 十一、执行记录与复测结果（已落地）

**落地版本**：gallery `21bbf547` / bench-template `32c9a85f`；基准 tag `perf-baseline-20261019`

### 11.1 等价性（开关式隔离，最干净的口径）

同一份代码、同一份数据，只切 `GALLERY_INDEX_CACHE`：

```
关缓存（=旧行为） vs 开缓存：8 个分类，count + images[].path 排序 sha256 ⇒ 不一致 0 个 ✅
```

> 踩坑记录：第一版验证脚本用「目录 basename」做 key，而 4 个分类同名 `(gamebanana)`
> ⇒ 互相覆盖、误报「哈希变了」。等价性比对必须用**完整路径**做 key。

### 11.2 性能（部署端实测，热态 3 次取中位）

| 分类 | 改前 | 改后 | 倍数 |
|---|---|---|---|
| 賽馬娘Pretty Derby | 2.02s | 0.21s | **9.6×** |
| 崩坏3 | 0.11s | 0.045s | 2.4× |
| 鸣潮 | 0.56s | 0.245s | 2.3× |
| 原神 | 1.71s | 0.855s | 2.0× |
| 星穹铁道 | 0.53s | 0.285s | 1.9× |
| 绝区零 | 0.52s | 0.31s | 1.7× |
| 尘白禁区 | 0.24s | 0.025s | 9.6× |
| 终末地 | 0.08s | 0.05s | 1.6× |

冷态（重启后首访）：0.53–2.82s，与改前同量级，未劣化。

### 11.3 目标达成情况（如实）

- ✅ 除原神外全部达成或超出预期
- ⚠️ **原神 0.855s 未达到 ≤0.5s 的目标**。归因（实测，非推测）：
  该分类单次响应体 **44,076,302 字节（44MB）**，索引读取已不是瓶颈，
  剩余成本在「遍历 7.2 万条 + JSON 序列化 44MB + 传输」。
  ⇒ 属于第十节「接口瘦身/分页」范畴，需单独排期；本次索引层优化已到其上限。

### 11.4 内存与回退

- 开缓存 RSS **606MB**（缓存本身上限 128MB，其余为堆与响应体瞬时占用）
- 更省：`GALLERY_INDEX_CACHE_MB=64`；完全关闭：`GALLERY_INDEX_CACHE=0`
- 整体回退：`git checkout perf-baseline-20261019`
