# 按需索引：两种粒度细化方案对照（2026-10-14）

> 前置结论（已定，不在此讨论）：索引根 `cache-index/`、不入库并加入自动更新排除、键编码可读化 + 冲突短哈希。
> 本文只解决一件事：**「一个分类一个索引」要不要含全量明细**。

## 0. 共同部分（两案都一样，先做完这层再选粒度）

### 0.1 新增 `server/lib/index-store.js`（零依赖）

| 函数 | 职责 |
|---|---|
| `slugKey(s)` | 目录/分类名 → 文件名安全键：`/` 与不安全字符换 `__`，中文/空格保留；超长或撞名追加短哈希 |
| `categoryDir(category)` | `<项目>/cache-index/<分类 slug>/` |
| `dirIndexPath(category, dir)` | 目录明细文件路径（A 案用；B 案不用） |
| `categoryIndexPath(category)` | 分类索引文件路径（两案都用） |
| `readJsonSafe(p)` / `writeJsonAtomic(p, obj)` | 读容错 / 原子写（临时文件 + rename，防半截文件） |
| `buildDirDetail(dir)` | **单层** readdir + stat + 图片过滤 ⇒ `{ dir, ts, dirMtime, images[] }` |
| `buildCategorySummary(category, dirs)` | 对给定目录列表汇总 `{ category, ts, dirs: { dir: { count, mtime } } }` |
| `isFresh(record, dir)` | 目录 `mtime` 未变且有记录 ⇒ 命中 |
| `rebuild({ category \| dir \| all })` | 重建入口（脚本/API 共用） |

### 0.3 路由与前端（两案差异只在「取数」这一步，接口形状一致）

- `/api/images?root=&path=`：命中索引则返回；否则**只扫该目录（单层）**建记录后返回
- 响应新增 `dirs`（当前目录的直接子目录名 + 计数），前端据此渲染「可进入的目录项」
- 前端 `browse/render.js`：进入目录才取数；**无直图时也渲染子目录项**，点击 `currentPath` 下钻
- 移除请求路径上的整树 `recursiveScanAll`（函数保留，不再由请求触发）

## 1. 方案 A：摘要式（分类索引 + 目录明细按需）— 推荐

### 1.1 文件布局

```
cache-index/<分类>/index.json                     ← 分类索引：只存目录级摘要
cache-index/<分类>/dirs/<目录键>.json              ← 目录明细：被访问到才生成/更新
```

### 1.2 体积与耗时（按实测数据推）

- 分类索引每条摘要约 100–160 B；`pawchive-pw` 分类顶层 461 个目录 ⇒ **约 50–80 KB** ⇒ 一次读取毫秒级
- 目录明细：单个目录的文件数 × 每条约 150–250 B；只有被访问的目录才建 ⇒ 单次读盘 = 该目录一层
- `find -maxdepth 2` 实测该根顶层两层仅 100 张图 ⇒ 首次访问该分类**几乎零成本**（只列 461 个目录名 + 摘要）

### 1.3 行为

- 进分类页 ⇒ 读 50–80 KB 摘要 ⇒ 立刻列出目录项（含每个目录的张数）
- 进某目录 ⇒ 若明细缺失或目录 `mtime` 变新，只扫该目录一层并写明细（几十 ms 级）
- 永不整树扫描；重建可按目录/分类/全量

### 1.4 代价 / 注意

- 索引文件数量 = 分类数 + **被访问过的目录数**（长期会增长到与「目录数」同量级 ⇒ 需要清理策略：
  例如「分类索引重建时顺手修剪不再存在的目录明细」）
- 「分类页显示每个目录张数」需要摘要准确 ⇒ 摘要随目录明细更新而回写（写放大很小）

## 2. 方案 B：一个分类一个大索引（含全量明细）

### 2.1 文件布局

```
cache-index/<分类>/index.json      ← 该分类全部图片明细
```

### 2.2 体积与耗时（按实测数据推）

| 分类 | 图片数 | 索引体积估算（每条 150–250 B） | 首次生成 |
|---|---|---|---|
| `pawchive-pw`（含 `/volume10/Resource/(Pawchive)/Pawchive`） | **341,523** | **约 51–85 MB** | **必须扫完整棵树**（已实测该规模扫描会打出 `scan:stat` 数十 GB、读 6.3 MB/s） |
| 其它 8 个分类 | 百~万级 | 数十 KB ~ 数 MB | 各自整树扫描一次 |

### 2.3 行为

- 进分类页 ⇒ 读整个分类索引（`pawchive-pw` 要读 51–85 MB 并解析 ⇒ 秒级甚至更久、内存峰值高）
- 任意目录页复用同一份内存索引 ⇒ 目录切换快（前提是索引已在内存）
- 目录有任何新增/改动 ⇒ 该分类索引需重建（或增量更新，实现复杂度上升）

### 2.4 代价 / 注意

- **首次生成即触发整树扫描** ⇒ 与「按需」的初衷相反，且正是此前把 NAS 拖慢的那种负载
- 分类索引动辄几十 MB：读放大、内存占用、写入时的原子写临时文件也大
- 好处是「一个分类一个文件」最直观、目录明细无需额外文件

## 3. 迁移与切换成本（两案之间）

- A → B：把 `dirs/*.json` 合并成分类 `index.json`（脚本可做，一次遍历）；B → A：拆分（按 `dir` 分组）
- 接口与前端**不需要改**（两案都返回同形状：`images` + `dirs`）⇒ 切换只动 `index-store.js` 的读/写实现
- 因此建议：**先按 A 落地**（先用得上、成本低），若日后确认想单文件，再跑一次合并脚本切到 B

## 4. 我的建议

**A（摘要式）**。理由用数字说：B 案在 `pawchive-pw` 上要 51–85 MB 单文件 + 一次 34 万张的整树扫描
（实测过的那种负载），而 A 案让「进分类页」只需读 50–80 KB、进目录才扫那一层 —— 两案的接口与前端完全相同，
**选 A 不牺牲任何体验，只省掉数十 MB 与一次全树扫描**；且将来要换 B 只需合并脚本。
